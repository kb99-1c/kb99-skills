# Код-ревью текущей ветки

Роль: старший эксперт-разработчик 1С:Предприятие 8.3 — стандарты ИТС, БСП, архитектура
прикладных решений, производительность запросов и кода.

Область ревью — **только изменения ветки**: коммиты `база..HEAD` и незакоммиченные правки.
Соответствие всей конфигурации стандартам — отдельная задача; находки вне диффа в отчёт
не идут (исключение — ошибка компиляции, см. 3.1).

Приоритеты по умолчанию, если пользователь не задал другие: корректность и риски ошибок →
архитектура и сопровождаемость → производительность → стандарты оформления.

## Порядок работы

1. Инвентаризация изменений — раздел 1.
2. Контекст из репозитория — раздел 2, до первого замечания.
3. Машинные проверки — раздел 3, параллельно с чтением диффа.
4. Разбор диффа по чек-листу — раздел 4.
5. Отчёт — раздел 5; в файл только по просьбе, раздел 7.

## 1. Что меняется в ветке

```powershell
python .claude/skills/code-review/digest.py                 # база: origin/dev, иначе dev
python .claude/skills/code-review/digest.py --base <ветка>  # явная база сравнения
python .claude/skills/code-review/digest.py --files         # полный список путей со статусами
```

Скрипт только читает репозиторий и печатает: базу и merge-base, число коммитов ветки, модули
BSL с построчными итогами и изменениями сигнатур `Экспорт`, изменения метаданных XML, правки
документации и инструментов, предупреждения — вендорский модуль БСП, `.bin`, удалённые файлы,
неотслеживаемые файлы.

Если `python` недоступен, те же данные дают `git status --short`, `git log --oneline <база>..HEAD`,
`git diff --stat <база>`, `git diff --name-status <база>`.

Дифф читается по модулям, с контекстом:

```powershell
git diff -U15 origin/dev -- "unload/cf/CommonModules/ВетИС_API_ОжиданиеСервер/Ext/Module.bsl"
git log --oneline origin/dev..HEAD -- "unload/cf/Documents/ВСД2_транзакция"
```

`git diff <база>` (без точек) сравнивает рабочее дерево с базой и включает незакоммиченные
правки; `git diff <база>...HEAD` — только коммиты ветки. Для ревью нужно первое: иначе
замечание легко дать по строке, которую в ветке уже исправили.

Номера строк в отчёте — по текущему файлу (чтение файла), а не по диффу: в диффе они смещены.

Если изменения большие (больше ~15 файлов или ~500 строк), разбор идёт по подсистемам
из `docs/Architecture.xml`: независимые модули можно отдать субагентам с этим же чек-листом,
а итог свести в один отчёт и убрать дубли. Порядок разделов отчёта при этом не меняется.

## 2. Контекст: что берётся из репозитория

| Что нужно | Где лежит |
|---|---|
| Назначение, тип конфигурации, версия | `AGENTS.md`, раздел 1; `README.md` |
| Режим совместимости и платформа | `AGENTS.md`, раздел 1: совместимость 8.3.14, платформа 8.3.27.2325 |
| Подсистемы, зависимости, потоки данных | `docs/Architecture.xml`, `docs/architecture/arch-*.xml` |
| Контракты экспортных методов | `docs/Contracts.xml` → `docs/contracts/contracts-*.xml` |
| Правила оформления кода | `docs/codestyle.md` — единственный источник; выжимка — `AGENTS.md`, раздел 8 |
| Якоря, контракты, теги журнала | `docs/1c-grace-rules.md` |
| Контексты модулей, экспорт, транзакции, запреты | `AGENTS.md`, разделы 6.1–6.5, 7 |
| Baseline проверки синтаксиса | `AGENTS.md`, раздел 6.5 |

Не спрашивать то, что написано в этих документах. Уточнять стоит только отсутствующее
в репозитории:

- ожидаемые объёмы данных и число одновременных пользователей — от них зависит приоритет
  замечаний по производительности и блокировкам;
- клиент-серверный или файловый вариант у конкретного заказчика;
- приоритет ревью, если ветка — срочная правка под клиента;
- назначение изменения, если из диффа и сообщений коммитов оно не читается.

Вопросы задаются одним блоком в начале, до замечаний. Если ответа нет, а оценка от него
зависит, — считать по худшему сценарию (клиент-сервер, рост данных) и указать это допущение
в отчёте.

## 3. Машинные проверки

### 3.1 Синтаксис и метаданные — MCP `onec`: два прогона и дельта

`check_configuration` отдаёт абсолютный список диагностик дерева, а не разницу с базой.
Поэтому ветка проверяется двумя прогонами — база (`merge-base`) и текущее дерево, — а вывод
сравнивается как множество строк. Сверка с фиксированным списком вместо прогона базы даёт
ложные замечания и пропускает повторные вхождения уже известных сообщений.

1. `mcp__onec__environment` — платформа доступна, `errors` пуст.
2. Прогон текущего дерева: `source.kind = "xml"`, `source.path = "<корень репозитория>\unload\cf"`,
   `modes = ["Server", "ThinClient", "ExternalConnection"]`, `extended = true`,
   `waitSec = 55`, `timeoutSec = 900`. Около пяти минут (306 с на 21.11.2026): запускать
   первым делом, дифф разбирать параллельно. Вернулся `runId` — забрать через
   `mcp__onec__get_run`, отменить — `cancel_run`. Текст результата сохранить в
   `build/review/onec-current.txt` (`build/` уже в `.gitignore`).
3. Прогон базы — только после первого, параллельно проверки не идут (`maxParallel = 1`):

   ```powershell
   git worktree add build\wt-base <merge-base>      # merge-base печатает digest.py
   ```

   Тот же вызов, но `source.path = "<корень репозитория>\build\wt-base\unload\cf"`; результат —
   `build/review/onec-base.txt`; затем `git worktree remove --force build\wt-base`.
4. Дельта:

   ```powershell
   python .claude/skills/code-review/onec-diff.py build/review/onec-base.txt build/review/onec-current.txt
   ```

   Код возврата 1 — есть новые диагностики. Скрипт сравнивает уникальные строки, а не
   количество: MCP схлопывает дубли, поэтому счётчики сверять нельзя.

Трактовка дельты:

- **новые строки** — «Критично» с точным текстом; для формы это чаще всего обращение
  к реквизиту, которого в конфигурации нет, или вызов без `Экспорт`;
- **исчезнувшие строки** — в резюме, если ветка правила этот код; иначе это смена платформы,
  режимов или выгрузки (тогда перегенерировать кэш);
- **пустая дельта** — одна строка в отчёте: «новых диагностик нет»;
- сверка с кэшем `onec-baseline.txt` (снимок базы `bc74cb04`: 33 диагностики) допустима,
  только если второй прогон сделать нельзя (нет прав на worktree, платформа занята); в отчёте
  тогда явно: «сравнение с кэшем от <дата>, база <sha>». Кэш, снятый с текущего дерева,
  тавтологичен: он совпадёт с прогоном ветки всегда и не проверяет ничего;
- если проверка не запустилась или не завершилась — «Ограничения анализа», а не выдуманный
  вывод о синтаксисе.

Что помнить при чтении списка: на платформе 8.3.27.2325 и текущей выгрузке диагностик три
десятка — 33 на базе `bc74cb04` и 30 на дереве ветки `feat/review3`, где вызовы `Ждать` заменены
на `ВыдержатьПаузу`. Все они — «Возможно ошибочное свойство / метод / параметр», следы
совместимости с УТ 10.3, УТ 11, КА и ERP. Одна ошибка из `AGENTS.md`, раздел 6.5, на текущей
выгрузке не воспроизводится (её снимали на 8.3.25.1374) — расхождение с документом,
а не замечание к коду.

### 3.2 BOM и переводы строк

```powershell
python tools/encoding-check.py            # всё дерево против dev
python tools/encoding-check.py --staged   # что попадёт в коммит
```

`.bsl` — BOM + CRLF (`AGENTS.md`, раздел 6.6). Расхождение в изменённом файле — «Важно»:
дифф превращается в «весь файл», `git blame` ломается, у модуля с защищённой поставкой
расходится `.bsl` и `.bin`. Исправление — `--fix`, но файлы правит автор ветки, не ревьюер.

### 3.3 Контракты и якоря — grace-audit

Запускается, если в диффе менялись объявления `Экспорт`, состав `GRACE:*` или граф:

```powershell
python tools/grace-audit/scan.py unload/cf tools/grace-audit/facts.json
python tools/grace-audit/anchors.py
python tools/grace-audit/validate.py
python tools/grace-audit/diff2.py
```

`validate.py` и `diff2.py` показывают расхождение кода с `docs/contracts/*.xml`: экспорт
без контракта, контракт без реализации, `@grace-depends` не совпадает с реальными вызовами.
Известное расхождение — `ВетИС_APIСервер.Площадка_Создать_Запрос` без `Экспорт`
(`AGENTS.md`, раздел 6.2), замечанием не считается.

Что в этом выводе не замечание, а шум или долг:

- `diff2.py` печатает вендорские модули БСП (`ФайловаяСистема*`, `ФизическиеЛица*` и подобные):
  они вне GRACE-области (`AGENTS.md`, раздел 3), их `@grace-depends` никто не заполняет;
- `КомандыВСД.Сервер` — 34 экспортных метода против 32 в контракте: `ОбновитьПартииПоГУИД_Фон`
  и `ОбновитьКоличествоПартий_Фон` объявлены ещё на `dev`, в контракт не внесены. Это долг
  репозитория, а не ветки; новым он не считается.

Расхождение считается замечанием ветки, только если метод или контракт появился в дифе.

### 3.4 API платформы

Любое сомнение в имени метода, свойства или сигнатуры — MCP `platform`: `search`, `info`,
`getMember`/`getMembers`, `getConstructors`. Доступность проверяется для режима совместимости
8.3.14, а не только для 8.3.27. Не нашлось — в отчёте писать «в API платформы не подтверждено,
требует проверки», а не называть метод по памяти.

## 4. Чек-лист

### 4.1 Корректность

- Пустые ссылки и `Неопределено`: обращение к реквизитам без проверки, пустой результат
  запроса, отсутствующая строка набора.
- Транзакции по шаблону `AGENTS.md`, раздел 6.3: `ОтменитьТранзакцию()` в `Исключение`
  до `ВызватьИсключение`; нет фиксации внутри `Исключение`.
- Блокировки: управляемые, минимальный охват, стабильный порядок захвата; нет длинной
  транзакции с ожиданием HTTP внутри.
- Асинхронность в клиентском коде: результат `ПоказатьВопрос`, файловых и длительных операций
  не используется до оповещения; обработчик оповещения не запускает второй параллельный вызов.
- Запросы: только `УстановитьПараметр`; нет конкатенации значений и подстановки имён
  из пользовательского ввода; `Выполнить`/`Вычислить` обоснованы и в безопасном режиме.
- Права: привилегированный режим минимальным охватом и с комментарием «зачем»; секреты
  и персональные данные не попадают в журнал регистрации (`AGENTS.md`, раздел 6.4).
- Контекст и `Экспорт`: у модуля-получателя есть нужный флаг (`AGENTS.md`, раздел 6.1),
  метод объявлен с `Экспорт` (раздел 6.2).
- Совместимость 8.3.14: нет методов новее режима совместимости; `ВызватьПаузу` запрещён,
  пауза — только через `ВетИС_API_ОжиданиеСервер` (`AGENTS.md`, раздел 7).

### 4.2 Архитектура и специфика конфигурации

- Код на своём месте: нет серверной логики в клиентском модуле или в модуле формы;
  модуль объекта — только логика объекта; бизнес-логика — в общем модуле подсистемы.
- У модуля одна ответственность; новый модуль — до 1000 строк; модулей «Утилиты», «Общее»,
  «Разное» не появляется (`AGENTS.md`, раздел 7).
- Программный интерфейс: `Экспорт` только для вызовов извне, разделы `ПрограммныйИнтерфейс`
  и `СлужебныеПроцедурыИФункции` разделены, экспорта «для себя» нет.
- Граф: новый межмодульный вызов отражён в `docs/Architecture.xml`, `GRACE:DEPENDENCY`
  совпадает с реальными вызовами, циклических зависимостей подсистем нет.
- Расширяемость: изменение проходит через точку переопределения (`ВетИС_ПереопределенияСервер`),
  а не зашито жёстко в одном месте; экспортные сигнатуры не ломаются без нужды — решение
  поставляемое.
- Вендорские модули БСП не правятся (`AGENTS.md`, раздел 3.3); единственное исключение —
  `УправлениеПечатью`, и его правка всё равно требует обоснования.
- Роли и RLS: изменённые роли дают минимально достаточные права, новых широких прав
  «на всё» нет; ограничения доступа не отключаются ради удобства.
- Интеграция: обмен, файлы, фоновые операции — механизмами БСП (`ДлительныеОперации`,
  `РаботаСФайлами`, версионирование), а не самописными очередями; HTTP — через существующий
  транспорт, а не новым `HTTPСоединение` на месте.
- Обновляемость: типовой функционал не дублируется, новые объекты — с префиксами `кб99_`
  и `ВетИС_`.

### 4.3 Производительность

- Нет `ВЫБРАТЬ *`; нет запросов в цикле (N+1) — пакетный запрос или временные таблицы.
- Виртуальные таблицы регистров читаются с отбором в параметрах, а не фильтрацией после.
- Соединения — по индексируемым полям; нет лишних `СГРУППИРОВАТЬ ПО` и подзапросов,
  заменяемых соединением; `В (&Массив)` большого массива — на временную таблицу.
- Нет полной перезаписи набора записей и лишних `Записать()` в цикле там, где достаточно
  точечного изменения.
- Длительные операции и массовая обработка — через `ДлительныеОперации` или регламентное
  задание, а не синхронно по кнопке.
- Клиент-сервер: нет вызовов сервера в цикле и на каждое изменение поля без нужды;
  на клиент не передаются большие таблицы.
- Кэширование повторных вычислений уместно и инвалидируется при изменении данных.
- Масштабируемость: оценка «что будет при росте данных в 10 раз» — полный перебор таблицы,
  выборка без отбора, обработка всех элементов справочника на лету.

### 4.4 Стандарты кода и БСП

- `docs/codestyle.md` — единственный источник; проверяется то, что менялось: имена, области,
  табуляция, «ё» в коде, неразрывные пробелы, пустые области, порядок разделов.
- У экспортных методов — доккомментарий с типами, блок `@grace-contract` и якорь
  `GRACE:CONTRACT`; `GRACE:DEPENDENCY` — только реально вызываемые модули.
- БСП вместо самописного: `ОбщегоНазначения`, `ОбщегоНазначенияКлиентСервер`,
  `СтроковыеФункцииКлиентСервер`, `ДлительныеОперации`, `ЖурналРегистрации`, `РаботаСФайлами`.
- Исключения: `Попытка` вокруг конкретной операции, а не вокруг половины процедуры; пустого
  `Исключение` нет; значимые ошибки — `ЗаписьЖурналаРегистрации` с тегом `[Модуль.Метод]`.
- Стандартные обработчики (`ПередЗаписью`, `ПриЗаписи`, `ОбработкаПроверкиЗаполнения`,
  `ПриСозданииНаСервере`) — по структуре БСП; `Отказ` не сбрасывается в `Ложь`;
  `СтандартнаяОбработка` не теряет ранее установленное значение.
- Магические значения: предопределённые элементы, перечисления, константы вместо строковых
  литералов и числовых кодов.
- Устаревшее: методы с пометкой «Устарела» в платформе и БСП, модальные вызовы в клиентском
  коде, `Сообщить()` вместо `ОбщегоНазначения.СообщитьПользователю()` там, где сообщение
  должно попасть в форму или отказ.
- Мёртвый код: закомментированные блоки, `TODO`, отладочные вставки, неиспользуемые параметры.

Если в диффе только документация и инструменты, категории 4.1 и 4.3 заменяются на корректность
скриптов и согласованность документов с кодом (`AGENTS.md`, раздел 10).

## 5. Формат отчёта

Один список замечаний, по убыванию критичности: Критично → Важно → Желательно → Стиль.
Внутри уровня — от «Корректность» к «Стандарты кода/БСП». Шаблон блока (пример формы,
не замечание по конкретной ветке):

```markdown
### [Важно] Отбор по измерению регистра накладывается после соединения
- **Категория**: Производительность
- **Расположение**: `unload/cf/CommonModules/<Модуль>/Ext/Module.bsl:<строка>`, `<Процедура>`
- **Проблема**: виртуальная таблица регистра читается целиком, отбор по измерению применяется к результату соединения.
- **Почему это важно**: на большой истории регистра запрос читает все записи вместо нужных; подбор партий замедляется линейно с объёмом данных и держит блокировки дольше.
- **Рекомендация**: перенести условие в параметры виртуальной таблицы:
  `РегистрНакопления.<Регистр>.Остатки(&Дата, Склад = &Склад)` вместо `ГДЕ Остатки.Склад = &Склад`.
```

Правила отчёта:

- «Расположение» — путь от корня репозитория, строка текущей версии файла и имя процедуры;
  для метаданных — вид и имя объекта плюс файл.
- «Почему это важно» — сценарий: какие данные, какое действие пользователя, какое последствие.
  Общие слова «может привести к ошибкам» не годятся.
- «Рекомендация» — что именно поменять; код — фрагментом до 10 строк, «было / стало».
- Ссылка на стандарт — по названию («Соглашения при написании кода», std453; `docs/codestyle.md`,
  раздел «Текст модуля»; `AGENTS.md`, раздел 6.3). Номер пункта — только если он есть
  в репозитории или в ИТС.
- Одно замечание — одна проблема; стиль не склеивается с корректностью.
- Замечаний нет — так и написать: «Замечаний, влияющих на корректность и сопровождение,
  не найдено», и перечислить, что проверено.
- Не выдавать за замечание то, что ветка уже исправила: сверяться с текущим файлом.

В конце — резюме:

```markdown
### Резюме

Вердикт: ОДОБРЕНО / ТРЕБУЕТ ИСПРАВЛЕНИЙ / БЛОКИРОВАНО

Состояние: ветка <ветка>, база <база>, HEAD <sha> — ревью относится именно к этому дереву.

| Критичность | Кол-во |
|---|---|
| Критично | 0 |
| Важно | 3 |
| Желательно | 5 |
| Стиль | 2 |

Системные выводы: 2–3 повторяющихся паттерна по ветке и что чинить первым.

Ограничения анализа: что не удалось проверить — нет вызывающего кода, не видно структуры
регистра, проверка синтаксиса не запускалась, тесты не прогонялись, объёмы данных неизвестны.
```

## 6. Границы

- Ревьюер не меняет код, метаданные, BOM/EOL и ничего не коммитит. Единственный файл,
  который он может создать, — отчёт по разделу 7.
- Код целиком не переписывается; предложения вне диффа — только если они прямо связаны
  с найденной проблемой.
- Методы, свойства и пункты стандартов не выдумываются: сомнение — MCP `platform`, иначе
  пометка «требует проверки».
- Замечания не придумываются ради количества; «замечаний нет» — нормальный результат.
- Ограничения анализа перечисляются явно, а не замалчиваются.
- Конфигурация — полная, не расширение (`AGENTS.md`, раздел 1): ссылка «так в типовой»
  источником правды здесь не является.

## 7. Отчёт в файл

По умолчанию отчёт выдаётся в чат. По просьбе пользователя — файл `.tasks/review/<ветка>.md`
в UTF-8 без BOM с CRLF, без коммита; в чат тогда — путь и резюме. Если замечаний больше
пятнадцати, файл предлагается, но молча не создаётся.

Нужна задача или комментарий в Redmine — скилл `redmine-issues`, проект `v8_dev_vetis`.
