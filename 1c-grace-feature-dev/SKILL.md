# 1C GRACE Feature Dev Workflow

Воркфлоу для разработки доработок в существующей конфигурации 1С:Предприятие
по методологии GRACE (Graph-RAG Anchored Code Engineering).

## Принципы GRACE

Три столпа, учитывающие sparse attention и RAG-навигацию LLM:
1. Семантический граф — явная карта зависимостей проекта
2. XML-разметка (якоря) — «глобальные токены» для sparse attention
3. Контракты — интерфейсы модулей как «семантический щит»

Порядок строго Top-Down:
```
Граф архитектуры → Контракты → Семантический каркас → Реализация → Верификация по графу
```

## Исполнение в DSH

Именованных агентов в DSH нет: роли ниже (`1c-grace-explorer`, `1c-grace-architect`,
`1c-grace-scaffolder`, `1c-grace-writer`, `1c-grace-reviewer`) — это отдельные вызовы
инструмента `subagent`.

- Промпт субагента самодостаточен: он не видит этот диалог. В промпт вкладывать цель,
  ограничения, пути к файлам и требуемый формат ответа; `cwd` — каталог проекта.
- «Параллельно» = все вызовы `subagent` в одном сообщении, а не по очереди.
- Результаты приходят уведомлениями; основной агент сам читает указанные файлы и сводит граф.
- Где нужен весь контекст задачи (реализация по утверждённому каркасу), уместен
  `subagent_fork` — он наследует этот диалог.

## Запуск

Загрузить навык `1c-grace-feature-dev` (в DSH — вызов инструмента `skill`) и сформулировать задачу:

```
Используй навык 1c-grace-feature-dev: добавить интеграцию с API складской системы
```

## Воркфлоу (8 фаз)

### Фаза 1: Discovery

Уточнение задачи. Если запрос неясен — задать вопросы о:
- Бизнес-проблеме и целевом результате
- Затрагиваемых объектах конфигурации (документы, справочники, регистры)
- Ограничениях (совместимость с типовой, обновляемость)

Сформировать цель в формате: «Цель: <что должно работать>»
Зафиксировать цель и ограничения.

### Фаза 2: Исследование и построение графа

Запустить **3 субагента параллельно** — три вызова `subagent` в одном сообщении, роль `1c-grace-explorer`:

- **Explorer 1 — похожие доработки**: как похожие задачи уже решались в этой конфигурации
- **Explorer 2 — архитектура области**: модули, подсистемы, общие модули, точки расширения
- **Explorer 3 — потоки данных**: регистры, документы, справочники, движения

Каждый субагент возвращает список файлов, фрагмент графа зависимостей в XML, обнаруженные паттерны.

**После возврата:**
1. Прочитать ВСЕ указанные файлы
2. Объединить фрагменты графов
3. Сверить с `docs/Architecture.xml` если существует

### Фаза 3: Контрактное уточнение

На основе графа выявить неоднозначности:
1. Точки интеграции — какие процедуры вызывать, какие контракты соблюдать
2. Граничные случаи — пустые табличные части, нулевые суммы
3. Обработка ошибок — блокировки, таймауты
4. Производительность — объёмы данных, частота вызовов
5. GRACE-логирование — какие точки требуют belief state

Представить вопросы списком. **Ждать ответов пользователя.**

### Фаза 4: Архитектура и контракты

Запустить **3 субагента параллельно** — три вызова `subagent` в одном сообщении, роль `1c-grace-architect`:

- **Минимальные изменения** — переиспользование существующего
- **Чистая архитектура** — отдельная подсистема, поддерживаемость
- **Прагматичный баланс** — скорость + качество

Каждый субагент возвращает: фрагмент Architecture.xml, контракты в формате Contracts.xml, оценку рисков.

Пользователь выбирает подход. После выбора:
1. Обновить `docs/Architecture.xml`
2. Обновить `docs/Contracts.xml`
3. Сохранить план в `.tasks/task-[name]/plan.md`

### Фаза 4.5: Семантический каркас ← ЯДРО GRACE

**После архитектуры, ДО реализации.**

Запустить субагента (`subagent`), роль `1c-grace-scaffolder`:

1. Создать файлы модулей с:
   - GRACE-якорями (`// @grace-module`, `// @grace-contract`, `// @grace-depends`)
   - Полными сигнатурами процедур/функций
   - Областями (#Область) по стандарту БСП
   - Заглушками тел (только `Возврат` или `ВызватьИсключение`)
   - Шаблонами GRACE-логирования (BELIEF/RESULT точки)
   - Комментариями `// LLM_NOTE:` для критических инвариантов

2. Создать `GraceЛогирование` если не существует
3. Сверить каркас с контрактами

**Каркас утверждается пользователем.**

### Фаза 5: Реализация

Запустить субагента (`subagent_fork` — он видит этот диалог и утверждённый каркас), роль `1c-grace-writer`. **Только после одобрения.**

Субагент заполняет тела процедур в каркасе:
- Соблюдает контракты из Contracts.xml
- Сохраняет ВСЕ GRACE-якоря
- Добавляет BELIEF/RESULT в точках IO/HTTP/БД
- Следует `rules/1c-grace-rules.md`

### Фаза 6: Верификация по графу

Запустить **3 субагента параллельно** — три вызова `subagent` в одном сообщении, роль `1c-grace-reviewer`:

- **Контрактная целостность** — контракты, сигнатуры, инварианты
- **Функциональная корректность** — баги, граничные случаи, безопасность
- **GRACE-соответствие** — якоря, логирование, belief state

Проблемы по важности: критично / важно / минорно.
При исправлении — итерация Фаза 5 → 6.

### Фаза 7: Self-correction loop

Если есть тесты (YAXunit, Vanessa Automation):
```
Тест падает → Субагент читает лог с GRACE-тегами →
Находит BELIEF_MATCH=false → Сверяется с контрактом → Точечное исправление
```

### Фаза 8: Итоги и обновление графа

1. Документирование: что построено, решения, файлы, контракты
2. Сверка Architecture.xml и Contracts.xml с реальным кодом
3. Обновление CLAUDE.md если появились правила (Fix-the-Rake)
4. Рекомендации по следующим шагам
